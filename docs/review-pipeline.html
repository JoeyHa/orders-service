Layer by layer

What each layer does, and the reason it exists.

L1 · Local pre-PRbuilt

/pre-pr skill: lint, tests, Docker build, then the diff-reviewer agent (Haiku, read-only). A Claude Code hook blocks gh pr create until a PASS exists for HEAD.

Shrinks the loop, doesn't enforce. A local finding costs seconds; in CI it costs a public comment, a push, a rerun and a notification. CI never trusts the local marker.

L2 · Issue-link checkbuilt

check_issue_link.py on closingIssuesReferences, via pull_request_target (script from main). No linked, open issue created or approved by someone other than the author → blocked. Bots, and break-glass applied by a maintainer, are exempt and logged.

SOC 2 change management: every change traces to an authorized request. A link proves traceability; authorization needs someone other than the author.

L3 · CI checksbuilt

lint, test (Postgres, alembic check), build. Required by branch protection. Runs PR code, so it holds no secrets.

Never spend tokens reviewing code that doesn't build. Cost: review latency now includes CI time.

L4 · Riskdesigned

Owner-defined floors from REVIEW.md (read from main), then a cheap classifier, then a blind adversarial verifier on anything still "low".

A wrong "low" ships unreviewed risky code; a wrong "high" wastes time. Effort goes where the error is expensive.

L5 · AI code reviewdesigned

Diff + issue + CLAUDE.md + REVIEW.md + touched files. Findings ranked important / nit / pre-existing, each with file:line. Checks issue fit and CLAUDE.md drift.

Pre-existing never blocks, nits are capped, documented decisions are not re-raised — repeated noise is why teams start ignoring reviewers.

L6 · Human approvaldesigned

0 / 1 / 2 approvers by risk via a custom required check. Bots comment, never approve. Stale approvals dismissed; most recent push must be approved.

Compliance may require a second person on every change — "low" may mean "approve", not "review deeply".

L7 · After mergedesigned

Telemetry, dogfooding, flags and canaries, one-click rollback.

Fast detection lets reversible, observable changes take a lighter bar. Silent, irreversible changes can't lean on it.

Trust boundaries

The code under review must never control its own review.

Runs PR code — no secrets

on: pull_request · workflow file comes from the PR branch
  • lint · test · build
  • Executes whatever the PR contains
  • Holds no tokens worth stealing

Reviews PR code — never runs it

on: pull_request_target · workflow file comes from main
  • Issue check · risk · AI review
  • Policy (REVIEW.md, CLAUDE.md, prompts) read from main
  • Diff read as data · agents get read-only tools, no Bash, no network
  • Token in an Environment locked to main
Never check out and execute PR code in a job that holds secrets — that's the "pwn request".
Why an Environment, not a repo secret: anyone who can push a branch can add a workflow that prints any repo secret. An Environment with "deployment branches: main only", used by a pull_request_target job, is out of reach of every branch.

Review rounds

Full review once, then only what changed — capped, with a full pass before merge.

Round 1Full review of the PR
Round 2Only last_reviewed..HEAD, touched files read in full
Round 3Incremental again
Cap hitPR is churning → hand to a human
Before mergeOne full pass

Rebase or force-push (last SHA no longer an ancestor) → full review. cancel-in-progress: two quick pushes pay for one review.

Evaluating the reviewer

The reviewer is code. It gets tests, versions and regressions like any other code.

Reverts & incidents
Each points to a PR the pipeline missed
Disagreements
Classifier vs verifier — the hard cases, human-labeled
Eval set
Replay each diff → expect the finding
Rescore on every change
Prompts, REVIEW.md, tool lists and model IDs are code — a PR changing them must pass the eval
Metrics
Recall on known misses · precision from human dismiss rate · format adherence · escalation rate
Pin model IDs, never aliases. model: haiku silently moves to a new version — the reviewer changes and nobody rescores.

What building L1 taught

Real observations from running the local reviewer on this repo.

"Non-blocking" can be wrong. Haiku rated a substring-matching hook as harmless; minutes later the same bug blocked our own workflow. A human reads the review, not just the verdict.
Format drifts on cheap models. A summary said "5 findings" over a list of 6. Format adherence is mechanically checkable — check it.
Reviewers re-raise settled decisions. Trade-offs already documented came back every round until marked with shortcut:. Repeated noise is how trust dies.
Same issue, two verdicts. A token-exposure finding was non-blocking on one run and blocking on the next — the only change was documenting the gap. Store one verdict per SHA, give blocking checks a human override, and define how documented trade-offs are graded.
Depth varies run to run. One review opened the hook script and caught a doc contradiction; the next only checked that paths exist. Docs that make claims about code need a rule to verify behavior, not just paths.
The gate caught its own operator. A marker written with a short SHA was rejected — the gate compares the exact full SHA a review vouches for.

Interview cheat sheet

QuestionShort answer
If L1 can be skipped, why build it?It shrinks the loop, not enforces. Cuts CI rounds and PR noise; CI never trusts a local marker.
Why not an LLM for the issue check?Anything a rule can decide, a rule decides — cheaper, faster, deterministic, auditable.
How is the verifier independent?Different model, blind to the first verdict, adversarial prompt. Its decision stands; it can only raise.
Why trust an LLM with risk at all?It can only escalate above owner-defined deterministic floors, never de-escalate.
How do you stop a PR gaming its own review?Policy from main; PR code is data; touching policy files = high risk.
pull_request vs pull_request_target?PR-branch workflow without secrets vs base-branch workflow with secrets. Never run PR code with secrets.
Where do review tokens live?An Environment locked to main, used by a pull_request_target job.
Prompt injection via the PR?User text is never evidence; agents get read-only tools, no network.
How do you keep developers from ignoring it?Count-first summaries, nit cap, file:line evidence, no re-raising, pre-existing never blocks.
How do you know it's any good?Eval set from reverts, incidents and disagreements; rescore on any prompt/tool/model change; pinned IDs.
Two runs, two verdicts?Store one per SHA, human override for blocking checks, explicit grading of documented trade-offs.
What does it cost per PR?Deterministic first; AI after green CI; depth by risk; incremental re-review; cancel in-progress.
Can a bot approve?Never. Comments and checks only; stale approvals dismissed.
Fail open or closed?Open where nothing is at stake (local hook); closed where a miss is expensive.
What decides how strict review is?Blast radius: reversibility, data, dependents, detection speed.
Isn't review the last line of defense?No — telemetry and rollback catch what review misses, and every regression becomes an eval case.
